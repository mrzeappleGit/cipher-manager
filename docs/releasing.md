# Releasing the Windows beta

## Prepare public source

Use a fresh export when the development repository contains private history:

```powershell
npm run export:public -- .release-private/public-source-review
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/scan-secrets.ps1 -Source .release-private/public-source-review -History
```

The exporter allows application source, build scripts, companion source and selected release documentation. It excludes Git history/tags, local agent instructions, historical planning documents, credentials, generated binaries and private audit files. It refuses existing destinations and linked files; use a new destination name for each export.

Review the complete export. Create a new Git repository from that directory with the public identity you intend to use (a GitHub noreply email avoids publishing a personal email). Keep the old repository private. **Making the original repository public still exposes its old commits, tags and existing release attachments**, even if its latest source is scrubbed. Replacing that history requires a separate reviewed rewrite and force-push procedure; this tooling never does it automatically.

The scanner is Gitleaks 8.30.1, downloaded from the official release and checked against its published checksum. Reports remain in .release-private and redact secret values. A passing pattern scan does not replace manual privacy review or prove that credentials were never exposed. Rotate any credential found in a shared history before removal.

## Build and check

```powershell
npm ci
npm run check
npm run release
```

The preparation script rebuilds both frontend variants, compiles serve, stages its target-suffixed executable, then Tauri builds the application and NSIS installer. The beta targets x86_64-pc-windows-msvc only. Do not publish a build made from stale dist or dist-snapshot content.

Version 0.2.0-beta.1 is aligned in the frontend/package lock, Cargo manifest/lock and Tauri configuration. Change them together for the next release; check:release verifies the main metadata. package.json remains private:true to prevent accidental npm publication; that does not make a GitHub repository private.

## GitHub workflow

.github/workflows/release.yml runs Windows checks, prepares/scans source, builds the installer and uploads artifacts. Third-party actions are pinned to verified immutable commits. Pull requests receive no release-writing job. Manually run the workflow on main with create_draft enabled to create a **draft prerelease**, after the build succeeds. Publishing it remains a manual action.

Release artifacts include the installer, a clean source ZIP, MIT/third-party notices, release notes and SHA256SUMS.txt. The workflow does not upload scanner reports, local settings or the development repository's .git directory. GitHub's own automatically generated source archives still represent the tagged repository: use the clean public repository for release publication.

## Signing

Unsigned beta builds are supported. For signed releases, configure Windows signing using [Tauri's official instructions](https://v2.tauri.app/distribute/sign/windows/) and protected CI secrets. Never commit a certificate/private key/password. No signing key or updater private key is generated by these scripts. Automatic updates are deferred; download installers from Releases.

## Publication gate

Review the exported source, complete docs/testing-windows.md, verify the checksums and notes, then publish the draft. Repository visibility changes and force pushes are not part of the build workflow. The MIT license covers project code; optional engines/models retain their own terms.
